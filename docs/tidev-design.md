# TiDev 设计文档

TiDev 是一个基于 Rust 和 ratatui 的终端编程助手，目标是在终端中提供高效的 AI 辅助开发体验。本文档描述 TiDev 的整体架构、界面布局和行为设计。

## 概述

TiDev 的设计参考了 OpenCode 的交互方式，目标是创建一个可扩展、响应迅速的终端 AI 助手。核心设计原则：

1. **分层架构**: 将用户界面、Agent 逻辑、模型请求和工具执行解耦，便于维护与扩展。
2. **终端优先**: 使用 Rust 与 ratatui 构建轻量 TUI，兼顾性能与可访问性。
3. **异步流程**: 通过异步事件和消息驱动机制，保持界面流畅并支持实时流式响应。
4. **可配置性**: 支持多模型、多 API 源和可定制工具，使用户可根据需求切换实现。

---

## 架构概览

TiDev 的主要模块包括：

- TUI 层：负责界面展示与用户交互。
- Agent 层：负责对话管理、上下文维护和任务调度。
- LLM 请求层：负责与模型服务通信，支持流式输出。
- 工具层：负责本地文件操作、命令执行和辅助工具。
- 配置层：负责持久化模型、会话和工作目录设置。

每个模块独立演进，避免业务逻辑和展示逻辑混合。

## 第一阶段设计

### TUI 架构

TiDev 的终端界面采用典型分区布局：主内容区、侧边栏和底部状态栏。

- 主内容区用于展示对话消息、助手输出和工具结果。
- 输入区用于接收用户指令和自然语言提问。
- 侧边栏用于显示工作目录、会话元信息、工具状态或快捷操作。
- 底部状态栏展示当前工作目录、模型状态、连接状态和提示信息。

界面通过 ratatui 的布局系统实现响应式分区，适应不同终端宽度与高度。

### 欢迎页面

应用启动时显示欢迎页面，用于首次配置或快速开始。布局参考 opencode：

- 顶部居中放置应用 Logo
- Logo 下方居中显示文本输入框，供用户输入问题或指令

欢迎页设计简洁聚焦，引导用户直接与 AI 交互。

### UI 布局

Session 视图采用双栏主布局：

- 左侧为消息与输入区：连续显示用户消息、助手回答、工具执行结果，并在底部保留输入组件。
- 右侧为侧边栏：展示文件上下文、工具快捷入口和会话状态。

这种布局旨在让用户在单一窗口内完成提问、阅读上下文、查看执行结果。

### 存储结构

TiDev 的配置文件与数据存储遵循 XDG 规范：

- **配置目录**: `~/.config/tidev/`
- **配置文件**: `config.toml`，包含默认模型标识、API 地址、超时策略等参数
- **数据目录**: `~/.local/share/tidev/`
- **认证文件**: `auth.json`，存储各 provider 的 API Key

具体配置格式可参考 opencode 项目。

### 会话存储

Session 数据使用 SQLite 持久化，包括消息历史、工具调用记录和工作上下文。后期可考虑基于 sqlite-zstd 实现透明压缩，以优化存储体积与查询性能。

### 模型配置

TiDev 的模型配置采用 Provider + 模型两级结构，支持多 Provider 切换：

#### Provider 级别

Provider 分为 `openai` 和 `anthropic` 两类，公共配置项包括：

- `base_url`：模型服务的 API 地址
- `api_key`：认证密钥（可从 `auth.json` 读取或环境变量覆盖）

#### 模型级别

每个 Provider 下可配置多个模型，模型配置项包括：

- `id`：模型标识符（如 `gpt-4o`、`claude-3-5-sonnet-20241022`）
- `display_name`：界面展示名称
- `context_window`：最大上下文窗口大小（输入+输出）
- `max_output_tokens`：单次输出最大 token 数
- `modalities`：支持的输入和输出模态，支持 `text`、`image`、`audio`
- `extra_body`：额外的请求体字段，供特定模型扩展使用

配置文件使用 TOML 格式，可参考 opencode 项目的配置方式。

模型配置模块负责验证配置完整性、加载默认预设，并暴露 Provider 与模型切换能力，使界面层仅关心当前模型状态。

### 模式

TiDev 使用运行时模式来控制主对话循环，而不是依赖固定的提示词预设：

- `build`：默认实现模式，允许工具调用和代码修改
- `plan`：只读规划模式，专注拆解任务、风险和假设

用户可以通过 `/mode build`、`/mode plan`、`/build` 或 `/plan` 切换模式。模型配置仍然可以提供自定义 `system_prompt` 作为基础提示词，运行时再叠加当前模式的提醒。

### LLM 请求层

LLM 请求层封装了与远程模型的交互，支持：

- OpenAI 风格的对话请求
- 流式响应处理，用于逐块渲染助手输出
- 模型服务差异抽象，方便后续接入更多提供商

该层也负责统一请求头、超时策略和错误处理，使 Agent 层只需关注消息传递。

### Agent 循环

Agent 循环是 TiDev 的核心控制逻辑，负责：

- 接收用户输入并将其纳入会话历史
- 向模型发送请求并监听流式结果
- 判断是否需要调用工具
- 执行工具后将结果回写到消息历史
- 根据模型与工具反馈调整状态流转

Agent 循环采用状态机思想，常见状态包括：空闲、思考中、执行工具、等待用户以及异常状态。

### 工具系统

工具系统为模型提供本地操作能力。设计目标是：

- 以“函数调用”形式向模型暴露工具能力
- 统一注册与描述工具接口
- 安全地执行文件读写、命令运行等操作
- 限制输出大小并在必要时截断以防界面拥堵

第一阶段将实现最基础的文件读取、写入与 Shell 执行工具，为后续扩展打底。
当前实现还补充了目录列表工具，方便模型更快建立工作区结构感。

### TUI 与 Agent 集成

界面与 Agent 之间通过事件与消息总线连接：

- 用户提交消息触发 Agent 循环
- 模型流式输出逐步推送到消息展示区
- 工具执行状态在侧边栏或消息流中体现
- Assistant 最终回复与工具结果同步写入会话历史

这种集成方式保证了前端界面与后端 Agent 逻辑的松耦合。

### Provider 引导

`/connect` 会先打开 provider 选择器，顶部提供搜索框，可按 provider id 或 display name 过滤已有 provider。列表底部始终保留 `Add new provider` 入口，选中后会进入同一个对话框里的 provider 向导。向导先收集 provider 信息和 API key，再逐个添加 model，并在每个 model 完成后询问是否继续添加。预设 provider 以 bundled catalog 的形式随二进制发布，在选择器里会标成 `preset`，用户自己创建的 provider 标成 `custom`。这样可以避免在配置文件里手工拼 TOML，也让新 provider 的接入路径保持在终端内完成。

## 后续阶段规划

### 第二阶段：完整工具集与权限系统

TiDev 将逐步扩展工具能力，并加入更细粒度的权限控制。主要设计方向：

- 工具扩展为文件编辑、模式匹配、内容搜索、任务管理、用户提问等。
- 权限系统可根据规则自动允许、拒绝或提示用户确认。
- 命令系统提供 `/help`、`/model`、`/clear` 等内置指令，改善用户控制体验。

### 第三阶段：会话管理与主题

会话管理模块负责：

- 将会话及历史消息持久化到本地
- 支持多个会话并在不同会话间切换
- 为不同项目或上下文保留独立历史记录

主题模块负责：

- 支持界面主题与配色方案
- 支持自定义布局与快捷键映射

---

## 总结

TiDev 的第一阶段核心目标是构建一个可用、稳定的 Rust 终端 AI 助手：

- 基于 ratatui 的终端界面，实现清晰的消息与工具布局
- 基于异步事件的 Agent 循环，支持流式模型响应
- 基本模型与工具能力分离，便于扩展与替换
- 强调可配置性、可维护性与终端可访问性

后续阶段将继续完善工具集、权限与命令体系、会话管理，并逐步引入 MCP 与 LSP 集成。
